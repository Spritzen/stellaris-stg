> **What** — the 2026-08-22 Vulcan session read end to end: `error.log` reconciled
> group by group against the 2026-08-10 baseline, and each inline observation
> from the run plan traced to a cause on disk.
> **Open when** — picking up work off that run, or before re-opening any question
> its observations touch.
> **Then** — [The run plan and its observations](../runs/vulcan-long-campaign.md) · [Live runs](../guides/live-runs.md) · [What the Federation run left open](../planning/ufp-run-remediation.md) · [Status](../planning/status.md)

The session was cut short — the player was called away roughly twenty-six
minutes into the game — so most of what the run was lengthened for
(dig sites, anomalies, story events, hulls above corvette) went **unreached,
which is unmeasured, not negative**. What it did reach was the empire designer,
and that turned out to be worth more than the play time.

**The headline is a pair.** The log is the cleanest this project has recorded —
**four post-init records against the baseline's 174** — and two of the three
Tier 1 fixes from 2026-08-10 are now confirmed in game by their own silence.
Against that, one throwaway line about a description box ("*shows
`vulcan_shipset_desc` instead of the actual description*") turns out to
condemn **half the shipset description file and every culture it does not
name**: 7 of 14 keys are dead and 23 flown cultures have no key at all.

### The shipset description box — one glance, thirty dead keys

Reported: *"Vulcan Description box shows `vulcan_shipset_desc` instead of the
actual description."*

The run plan predicted an **empty** panel. It is worth correcting the
expectation: Stellaris renders an unresolved localisation key as **the raw key
text**, so "the box shows the key" is the normal signature of a missing key, not
of a different defect.

The plan had already spotted that Vulcan flies the `vulcan` culture while the
description is keyed `vulcan_01`. Sweeping the rule rather than repairing the
instance — [live-runs.md](../guides/live-runs.md#a-screen-nobody-opened-is-a-check-that-never-ran)'s
standing requirement — the damage is far wider:

- **41 graphical cultures are declared** in the merged tree.
- **14 `_shipset_desc` keys exist**, all in one file — ours, at
  [`src/localisation/english/stg_shipsets_l_english.yml`](../../src/localisation/english/stg_shipsets_l_english.yml),
  reached in the merge at `stg-build/localisation/english/`.
- **23 cultures that a prescripted empire actually flies have no key at all**:
  `borg`, `caitian`, `cardassian`, `dominion`, `elachi`, `ferengi`,
  `generic_01`, `generic_02`, `generic_05`, `generic_06`, `generic_07`,
  `krenim`, `lukari`, `malon`, `starfleet_tng`, `suliban`, `terran_nx`,
  `tholian`, `tuterian`, `vidiian`, **`vulcan`**, `xindi`, `yridian`.
- **7 of the 14 keys name a culture no empire flies** and can never render:
  `borg_01`, `cardassian_01`, `dominion_01`, `federation`, `ferengi_01`,
  `tholian_01`, `vulcan_01`.

**Only 7 of the 14 descriptions can ever appear**, and the seven that work
(`andorian_01`, `bajoran_01`, `bolian_01`, `breen_01`, `federation_32`,
`klingon`, `romulan`) are the STNH-art sets. Every Walshicus set — including the
Federation's own `starfleet_tng` — shows a raw key. The prose is written and
good; it was written against the *city-set* culture names instead of the
*shipset* ones. Finding 3.

### Finding 1 — the female master clothes selector was never patched

**Tier 1 — root cause confirmed, fix is mechanical.**

All three post-init log records are one defect with two shapes, and **all three
target files exist on disk**:

| Record | Row | Shape |
|---|---|---|
| `…/sth humanoid 08/sth_humanoid_08_female_clothes_01` | `humanoid_master_female_clothes_01.txt:400`, `:2532` | **no `.dds`** |
| `…/sth humanoid 08/sth_humanoid_08_female_clothes_02` | `humanoid_master_female_clothes_01.txt:401` | **no `.dds`** |
| `…/brunali/norcadian_female_clothes_04.dds` | `humanoid_master_female_clothes_01.txt:544` | **wrong directory** — the file lives under `norcadian/`, and line 534 in the same file names it correctly |

The 29 patches that landed on 2026-08-10 hit
`humanoid_master_male_clothes_01.txt` (seven president rows) and the Terran
ruler's doubled `.dds.dds` (22 rows). **The doubled extension is genuinely gone —
zero occurrences tree-wide.** But the female master's equivalent rows were never
touched, and **`ufp-run-remediation.md` claims "Both files now hold zero
malformed paths", which is contradicted by the tree.**

Sweeping the rule across all 201 selector files: **11 extension-less rows
remain, 10 of them in the female master**, and every one of the ten resolves the
moment `.dds` is appended:

```
humanoid_master_female_clothes_01.txt:400,401,2532  sth humanoid 08/sth_humanoid_08_female_clothes_01, _02
humanoid_master_female_clothes_01.txt:2787-2793     federation_president_female_1, human_president_female_1-5, civ_human_female_clothes_16
humanoid_master_male_clothes_01.txt:2494            sth humanoid 08/sth_humanoid_08_male_clothes_01   ← file genuinely absent
```

**The seven `human_president_female_*` and `federation_president_female_1` rows

and they are still broken. The eleventh row is the only one where the art really
is missing: `sth_humanoid_08_male_clothes_01.dds` exists in no source mod
(`_02` through `_04` do), so that one belongs with the dangling paths, not with

### Finding 2 — six declared cultures have no city art, and four city sets are named by nobody

**Tier 1 — confirmed on disk; the player-visible half is Tier 2.**

`stg_graphical_culture.txt` declares ten cultures for their **ship** art.
A `graphical_culture` declaration is also what makes a **city** style offerable
— that is [decision 62](../decisions/62-city-set-cultures-undeclared.md)'s
mechanism read forwards instead of backwards. Six of the ten
(`bajoran_01`, `federation_32`, `andorian_01`, `bolian_01`, `breen_01`,
`generic_07`) have **zero** `<key>_city_l*.dds` in the tree.

Symmetrically, six city sets in
`stg-build/gfx/portraits/city_sets/` — `generic_01` through `generic_06`,
11 layers each, all at 800×400, all from STNH — are named by **no**
`city_graphical_culture` anywhere in
[`src/prescripted_countries/`](../../src/prescripted_countries/).

**`check_room_references` question 5 cannot see either half.** It asks whether a
`city_graphical_culture` that an empire *names* has `<name>_city_l01.dds` behind
it. Both populations here fail the *other* direction: a declared culture with no
art, and art with no namer. That is
[decision 34](../decisions/34-src-shadows-drop-source-declarations.md)'s rule
one more time — "declared somewhere is not declared where the engine looks" —
and the check needs the reciprocal question added.

The content call is separate and is genuinely a call: give the five STNH-art
playables (`bajoran_01`, `federation_32`, `andorian_01`, `bolian_01`,
`breen_01`) their own city sets by pointing them at one of the six orphans, or
leave them on `humanoid_01` as their prescripted entries already do and accept
that the designer offers a style that draws nothing.

> **Struck 2026-08-22 — not a defect, and there is no content call.** A missing
> city set does not draw nothing; it draws its `fallback`. Vanilla says so in
> the header of the very file this finding read:
> *"Setting fallback will allow the game to try and use another culture if the
> asset is missing"* (`00_graphical_culture.txt`), and all six of these declare
> `fallback = mammalian_01`, which ships art.
>
> **The premise could never have held**: **24 of vanilla's own 52 declared
> cultures ship no city art either** — 46%. Narrow to the cultures actually
> offered (no `randomized = { always = no }`) and vanilla has two, both with a
> fallback. Follow the chain and vanilla is **0 of 22** and STG **0 of 41**.
> That invariant is now `check_graphical_culture_art`.
>
> The orphaned `generic_01`–`generic_06` art is a reachability question that
> `check_unreferenced` already asks — `gfx/portraits/city_sets` is one of its
> closure roots — under [decision 45](../decisions/45-clutter-pass.md)'s
> report-tier policy. **This finding was a measurement taken without reading
> vanilla's own file header**, which is the same shape of error as finding 5.
> [Decision 84](../decisions/84-shipset-descs-and-home-system-names.md).

### Finding 4 — two bodies in 40 Eridani share a name

**Tier 2 — small, certain, one edit.**

`stg_home_systems.txt` gives "Kerkhov's Moon" to both a moon of `40 Eridani C`

ask for one.

> **Fixed 2026-08-22 — and "small, certain, one edit" was wrong on all three
> counts.** Swept across all 37 generated home systems it is **seven duplicate
> names in six systems from three unrelated causes**, and the file is
> GENERATED, so none of them is an edit here:
>
> * **`sub_blocks` matched at every nesting depth** while its docstring promised
>   immediate children. STNH writes Kerkhov as a planet *nested inside* the star
>   40 Eridani C, so its moon was emitted under the star as well as under
>   Kerkhov. Two systems, two duplicates.
> * **the star/capital de-collision rule only knew `pc_<x>_star`**, and the
>   generator's commonest star is the bare `star` keyword — so **Qo'noS, Cait,
>   Romulus and Haakon** each drew their capital's name twice. Fixed by
>   *dropping* the colliding name, not replacing it: 23 STG empires render the
>   same string for system and capital, so substituting the system key changes
>   nothing a player sees, and **12 of vanilla's 16 `custom_empire` star bodies
>   carry no name at all.**
> * **STNH names both moons of S'latas "S'latas a"** — their content, their own
>   suffix convention, so the second becomes "S'latas b"
>   ([decision 12](../decisions/12-fix-source-errors-dont-drop.md)).
>
> `check_home_system_body_names` guards it, scoped to `usage = custom_empire`
> because vanilla fails the question **62 times in 357** initializers overall and
> **0 times in 9** home systems.
> [Decision 84](../decisions/84-shipset-descs-and-home-system-names.md).
